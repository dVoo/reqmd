## IMP-parser-goldmarkParsers-5af47b6: goldmarkParsers
```attr
status: approved
x-reqmd.imported: true
x-reqmd.source-file: internal/parser/parser.go
x-reqmd.source-line: 44
x-reqmd.symbol-kind: var
trace: []
```

goldmarkParsers is a pool of goldmark parsers. The goldmark Markdown
type is NOT safe for concurrent use; instead, each goroutine in the
per-file worker pool `Get`s a parser, parses one file, and `Put`s it
back. The pool is initialized lazily on first use.

The expensive part of goldmark.New is the extension registration
(GFM, mermaid, fences, highlighting, emoji, meta, katex) — those
have heavy internal data structures (chroma lexers, KaTeX specs,
emoji tables, meta parser, etc.) that are reusable across parses.
Reusing parsers via sync.Pool avoids the ~216 µs per-file cost of
re-constructing that state on every parseMD call.

## IMP-parser-parseMDLightweight-b969c68: parseMDLightweight
```attr

x-reqmd.source-line: 588
x-reqmd.symbol-kind: function
trace: []
```

parseMDLightweight is the lightweight counterpart of parseMD: it
walks the goldmark AST to find heading+attr-block pairs, but stops
after extracting the ID and the trace list. It skips the full
YAML unmarshal of the attr block, the body text accumulation, and
the rationale extraction.

The goldmark parser is borrowed from the shared goldmarkParsers
pool (same as parseMD) — goldmark.Markdown is not safe for
concurrent use, but the per-file worker pool guarantees exclusive
access during a single parse.

Sub-req hierarchy is intentionally NOT tracked: the lightweight
index only needs ID and trace. Caller-side graph code can detect
hierarchy via the heading level (level+1 == child of preceding
level heading) if needed.

## IMP-parser-traceScanRe-7583aee: traceScanRe
```attr
status: approved
x-reqmd.imported: true
x-reqmd.source-file: internal/parser/parser.go
x-reqmd.source-line: 549
x-reqmd.symbol-kind: var
trace: []
```

traceScanRe extracts just the trace list from an attr-block string.
Faster than yaml.Unmarshal because it only scans for the `trace:`
key and parses the list of values, ignoring all other fields.

Limitation: only the multiline form

trace:
- ID-001
- ID-002

is supported. The inline form `trace: [ID-001, ID-002]` is NOT
captured here. The heavyweight validator runs later on the scoped
subgraph, where the inline form will be caught during full parse.
Authors who care about scoped-check indexing should prefer the
multiline form (which is the project's documented style anyway).
