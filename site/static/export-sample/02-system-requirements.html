Document format and content model

#

How a requirement document is written and what a parse yields.

SYS-FMT-001 Markdown requirement format

#

Each requirement shall be authored as a Markdown heading of level 2 or deeper followed immediately by a fenced ```yaml reqmd ``` YAML block, then free-form prose. The fence info string shall be yaml reqmd, whose leading yaml tag gives the block YAML syntax highlighting in editors and on GitHub; the bare reqmd fence shall also be accepted, and the importer shall always write the highlighted form. The heading text is the requirement ID; an optional human-readable title may follow the ID after a colon and space (e.g., ## REQ-001: Login requirement). A heading is a requirement exactly when its next AST sibling is a ```yaml reqmd ``` fence — requirement depth is not fixed, so any h2+ heading with an adjacent reqmd block is a requirement and its parent is the nearest enclosing requirement (SYS-CON-001 defines the headings that are not requirements). An optional *Rationale:* paragraph may follow the prose statement and is extracted from the body.

A level-1 heading is the document title and can never be a requirement: a reqmd block under a level-1 heading is a parse error.

SYS-FMT-002 Built-in attribute system

#

The reqmd block shall support six built-in attributes — trace, status, disposition, disposition-reason, version, and requires-trace-from — that carry tool-level semantics in Pass 2 validation. Built-in attributes are injected automatically and must not be declared in schema.yaml. The parent-child relationship between requirements is structural (derived from the heading hierarchy in the parser), not an attribute — no parent built-in is needed. A document may additionally declare a project-defined verify attribute naming the verification method; an approved requirement carrying it is treated as a verification measure by the verdict checks (SYS-VAL-002).

Details2 attributes · traces
Priority
Critical
Status
approved
Rationale:

Separation of concerns: project-specific attributes go in schema.yaml; tool-level attributes are always available without schema boilerplate. Blocking redefinition prevents ambiguity. Keeping the parent relationship structural avoids redundant data — the heading hierarchy is the source of truth.

SYS-FMT-003 Schema.yaml document configuration

#

Each document directory shall contain exactly one schema.yaml that defines project-specific attributes using JSON Schema 2020-12 (YAML-serialized). An optional x-reqmd extension block provides directory-level metadata (level, document-id, upstream, id-prefix, external, mandatory-disposition, url, source, requires-trace-from, ignore-status, additional-status-values, disjoint-check).

The external: true flag marks a directory as a proxy for artefacts originating outside authored reqmd specs (standards, architecture tools, test frameworks). Proxy directories suppress the untraced WARNING globally. The url field provides a human-readable link; the source block (path + format) drives planned reqmd-scan generation.

x-reqmd.requires-trace-from sets a document-wide default coverage expectation: an array of document-id or level tokens using the same vocabulary as the requires-trace-from attribute. Every requirement in the document that does not declare its own requires-trace-from attribute inherits this default; a requirement that declares the attribute overrides it entirely (no merging), and requires-trace-from: [] opts that single requirement out of downstream coverage. A document without a default leaves its requirements on the generic boundary-inference fallback. The default is validated at schema compile time (an array of strings matching the attribute token pattern ^[a-z0-9_-]+$, no duplicates); an empty default list means every requirement in the document expects no downstream coverage. Default tokens resolve exactly like per-requirement declarations (SYS-FMT-005).

Export output filenames follow the convention <dirname>-requirements.<ext>, written alongside each document directory or into -o <dir> if specified.

Priority

Status

Rationale:

JSON Schema 2020-12 is a widely-supported standard with validators in every language. The x-reqmd block keeps reqmd-specific configuration in the same file without breaking standard JSON Schema validators.

SYS-FMT-004 YAML frontmatter support

#

A .md file MAY begin with a YAML frontmatter block delimited by ---. It SHALL be parsed as document metadata and SHALL NOT contribute a content-tree node or body prose. Metadata from the files of one document directory SHALL be merged with first-file-wins semantics. The description key SHALL be rendered as document-level prose below the document header in the HTML export. Frontmatter parsing must not interfere with requirement attr-block parsing within the same file, and a --- thematic break further down a file remains body content.

Details2 attributes · traces
Priority
High
Status
approved
Rationale:

YAML frontmatter is the convention every Markdown toolchain uses (Jekyll, Hugo, GitHub Pages), so authors arrive expecting it to work; a document can then carry an abstract or a navigation hint without a separate file. Metadata is deliberately content-free: it never becomes a requirement, so it can never be traced, counted, or filtered. Document configuration stays in schema.yaml, the one manifest per directory that is validated at compile time (SYS-FMT-001).

SYS-CON-001 Content tree — nothing dropped

#

The parser shall capture the full document content as a content tree in which every heading is a node except the level-1 document title, and every node is exactly one of two kinds: a heading followed by a reqmd block is a requirement; every other heading, and prose preceding the first heading, is a section. Whether a section behaves as a folder (has children) or as a leaf prose block shall be derived from its children at render time and never stored, so adding a subsection cannot change a node's kind. A level-1 heading shall be treated as the document title, not content: it is captured as the document title, is never a content node, and must not carry a reqmd block — requirement headings shall be level 2 or higher, a level-1 heading with a reqmd block is a parse error, and a level-1 heading that is not the first heading of its file is a parse error as well (only the first h1 names the document; a later one would have its text silently dropped). Prose, code blocks, and thematic breaks shall attach to the nearest open node's body. No content shall be dropped: leading prose, requirement-less files, and headings without attributes are all preserved as nodes.

Details2 attributes · traces
Priority
High
Status
approved
Rationale:

Requirements documents carry structure and narrative beyond requirement records. Dropping non-requirement content (as early prototypes did) made exported pages silently incomplete. The tree keeps document order and hierarchy faithful to the source so ls, stats, CSV, and HTML can render the document as written, not just its requirement subset.

SYS-CON-002 Items in output commands

#

Sections shall be visible in ls (a leading Type column — req/section — with section rows showing heading text), stats (per-document item counts plus a type breakdown), CSV export (a Type column, rows in document order), and HTML export (collapsible folders for sections with children, plain blocks for leaf sections and the document preamble, and sidebar TOC entries). Sections shall have no attributes and shall not participate in validation, trace checks or coverage. --filter shall prune requirements and keep a section only while it still leads somewhere: a section with surviving children is kept, a section whose children were all pruned is dropped (its prose introduced content the filter removed), a bare heading with neither prose nor rationale is dropped, and a section that never had children but carries prose or a rationale (a leaf information item, or the headingless document preamble) is kept. The prune rule is presentational only and shall not change the requirement set used by check, which stays requirement-scoped.

Rationale:

Items are presentation, not specification: they carry no schema-validated data, so no graph check can attach to them. Keeping them out of validation prevents noise while still rendering the authored document faithfully.

Validation and checks

#

What is validated, which checks run over the tree, and how findings are scoped and suppressed.

SYS-VAL-001 Multi-pass validation pipeline

#

The validation pipeline shall execute four passes in this order: Parse (goldmark AST), Pass 1 (JSON Schema validation with built-in injection), Graph build (pure Go in-memory adjacency with three sub-passes: node creation, trace-edge building, parent-child edge building), and the graph check pass, which reports this catalog (check code, severity, condition):

  • broken-ref (WARNING) — a trace target does not resolve; a broken parent reference from the parent-child sub-pass is an ERROR.
  • duplicate-id (ERROR) — two requirements claim the same ID; the first definition wins.
  • ambiguous-ref (ERROR) — an unqualified reference matches an ID that exists in several documents; the qualified form is required.
  • circular (ERROR) — the trace graph contains a cycle.
  • untraced (WARNING) — no inbound reference, and the requirement is neither at a root or leaf boundary nor a sub-requirement.
  • no-downstream (WARNING) — no outbound reference, and the document is not at a leaf boundary.
  • requires-trace-from-coverage (WARNING) — a declared or inherited coverage expectation is unmet; an expectation naming neither a document-id nor a level also warns.
  • disposition-reason (WARNING) — a non-implemented disposition carries no reason.
  • mandatory-disposition (ERROR) — a document with mandatory-disposition: true has a requirement without a disposition.
  • id-prefix (ERROR) — an ID does not match its document's id-prefix, or two documents claim the same prefix.
  • version-pin (ERROR) — a ~N pin disagrees with the upstream's version; direction outdated is demotable to WARNING by --relaxed-versions, direction predated never is.
  • missing-verdict (WARNING) — an approved verification measure has no result.
  • failing-verdict (ERROR) — a measure's rolled-up evidence is fail.
  • disjoint-attribute (ERROR) — a trace link connects requirements with no overlapping value for a disjoint-checked attribute.
  • unbound-result (WARNING) — a loaded verification entry declares x-reqmd but binds to no requirement; suppressed by --ignore-unbound-results.
  • verdict (INFO) — the rolled-up outcome of a measure that has evidence; never affects the exit code.

Graph construction shall run concurrently with Pass 1 validation — it only reads the parsed tree — and its result shall be consumed after Pass 1 completes, so graph checks still run after validation.

ERROR-level results produce exit code 1; WARNING and INFO results do not.

Document discovery follows a recursive tree walk: every directory containing a schema.yaml is a document directory; all *.md files in that directory (non-recursive) are parsed against that directory's schema.

Properties are ordered in ls and CSV export as: required attributes first (in schema's required order), then optional attributes (in schema definition order), then built-in attributes.

The untraced check is suppressed for sub-requirements (IsChild flag set during graph construction), as their parent relationship provides the necessary trace context. Broken parent references discovered during the parent-child sub-pass produce ERROR-level results. Every check may be suppressed per requirement (SYS-SUP-001).

The disposition workflow is defined as:

  • No disposition set → downstream traces expected (no-downstream is WARNING)
  • disposition: implemented → downstream traces expected; no-downstream is WARNING
  • disposition: deferred → no downstream traces expected; disposition-reason is REQUIRED
  • disposition: rejected → no downstream traces expected; disposition-reason is REQUIRED

Explicit reqmd:trace <symbol> directives are resolved and validated by reqmd-code at extraction time (SYS-IMP-001), before a bundle exists; this pass validates the emitted requirement-ID references.

Defining a reserved built-in attribute in schema.yaml produces a compile-time error.

SYS-VAL-002 Verification result ingestion and outcome-gated checks

#

The check and serve commands shall accept a repeatable --results <path> flag that loads ephemeral verification results from CTRF JSON reports (automated tests) and manual-results markdown directories (review, inspection, analysis). Each path is auto-detected: directories are walked, .ctrf.json and CTRF-shaped .json files are parsed as CTRF, subdirectories with a schema.yaml are loaded as manual results via the standard document pipeline, and non-CTRF files are skipped silently. Single files are parsed as CTRF.

Results are loaded per invocation and are not persisted in the spec repo. CTRF test entries map to verification measures via the x-reqmd.id extra field (with optional ~N version pin). CTRF status maps to a reqmd outcome (passed→pass, failed→fail, skipped→skipped, pending|other|flaky→inconclusive). Manual results carry x-reqmd.outcome, x-reqmd.verifier, x-reqmd.evidence, x-reqmd.verified-at, and trace: [MEASURE-ID]. x-reqmd.verified-at shall accept an RFC 3339 date-time (the canonical form, matching CTRF stop) or a bare YYYY-MM-DD date, which means midnight UTC. Across all inputs, the latest result per (measure, case) wins by timestamp.

Each merged result is synthesized as a pseudo-requirement (RESULT:<measure>, or RESULT:<measure>#<case> for a case-keyed result, with trace: [MEASURE-ID~N], x-reqmd.outcome: <verdict>) appended to the document slice before graph build. Result attributes are tool-owned and namespaced under x-reqmd.* so they never collide with authored schema attributes. Two outcome-gated checks run when result nodes are present: missing-verdict (approved measure with no result, WARNING, suppressible) and failing-verdict (latest result is fail, ERROR, suppressible). The existing version-pin check applies to result→measure traces, reusing stale-verdict detection with no new logic. Draft measures are skipped by missing-verdict.

CTRF entries may additionally carry x-reqmd.case, x-reqmd.verifies, and x-reqmd.description so a run binds through an explicit test case: id alone attaches the result directly to a measure; case + verifies (or verifies alone, keyed by the normalized (suite, name)) synthesizes a test case whose trace edges target the verified requirements and whose body is the description. Results merge latest-wins per (measure, case) by CTRF stop. Outcome-gated checks roll up a measure's evidence over its own results and its approved downstream test cases (authored or synthesized) with strict aggregation (any fail → fail, else inconclusive → inconclusive, else skipped → skipped, else pass); draft downstream cases are reported as ignored, and deferred/rejected measures are exempt. check accepts --ignore-unbound-results to suppress unbound-result warnings for entries that declare x-reqmd but bind to nothing; instrumented entries binding nowhere surface as broken references.

A measure whose evidence set is non-empty additionally emits an INFO verdict result naming the rolled-up outcome, so a clean run with --results is visibly distinct from a run without results. Findings attributed to result nodes are grouped in a verification-results section of the text report and in a results array of the JSON report.

SYS-CHK-003 Disjoint-attribute consistency check

#

The check command shall accept a repeatable --disjoint-check <attr> flag (and the equivalent x-reqmd.disjoint-check key in schema.yaml, string or array) that, for every trace link, verifies that the source and target requirements have at least one overlapping value for the named array-typed attribute. A zero intersection shall produce an ERROR (disjoint-attribute); an empty or absent value is exempt ("applies to all"). The check shall be suppressible per requirement via reqmd-suppress: [disjoint-attribute].

They turn a manual review convention into an enforceable CI check with a single flag, without adding a new built-in attribute.

SYS-STS-001 Requirement status lifecycle

#

status shall be a built-in attribute with enum [draft, approved]; a missing status shall default to approved (silently). Only approved requirements shall count as upstream coverage providers — a draft requirement referenced by a trace shall NOT satisfy a requires-trace-from expectation. Schemas may extend the enum via x-reqmd.additional-status-values (lowercase-only values, no built-in collision, no duplicates) or opt out of the lifecycle per document via x-reqmd.ignore-status: true (all requirements become coverage providers; the status filter is hidden in HTML export). When a missing-coverage message is produced and at least one inbound was filtered by the status gate, the message shall report how many draft downstreams were ignored.

Rationale:

A lifecycle axis distinct from disposition lets teams keep in-progress requirements in the spec without letting them (falsely) satisfy coverage. Draft requirements remain traceable and validated, but cannot close a coverage expectation until promoted to approved.

SYS-FIL-001 Generic attribute filtering

#

The check, ls, stats, export csv, export html, export json, and baseline diff commands shall accept a --filter "<expr>" flag that scopes the operation to requirements matching an expression evaluated against the requirement's attributes plus the built-in id, title, status, disposition, trace, and version variables. serve shall take no filtering flag: the live preview always contains the whole tree and the HTML viewer scopes itself from URL state. Expressions shall be compiled once at startup into bytecode, and compile-time validation shall reject expressions referencing attributes not declared in any schema.yaml (global typo check). Per-document attribute absence shall evaluate to nil rather than erroring.

Those commands and baseline diff shall also accept --relaxed-filter, which shall downgrade the typo check to a warning and admit any attribute actually present on a requirement even when no schema declares it, so an attribute set used in reqmd blocks without a schema change remains filterable.

Coverage checking shall be filter-aware: a filtered-out requirement cannot satisfy the requires-trace-from expectation of a filtered-in requirement, so filtered-out requirements do not cause false coverage failures. The graph is always built from the full tree so trace refs to filtered-out requirements still resolve; only per-requirement checks and coverage are scoped. baseline diff shall additionally accept --filter-a and --filter-b to compare two filtered views of a single commit (e.g. "what does Premium add over Base").

Details2 attributes · traces
Priority
Medium
Status
approved
Rationale:

Large specs make full-tree review and incremental CI expensive. Attribute filtering lets teams scope check, exports, and diffs to the slice of the tree that a change touches, without losing the ability to resolve traces globally. Rejecting undeclared attribute names at compile time catches typos before they silently match nothing (with --relaxed-filter available where a tree intentionally carries informal attributes), and filter-aware coverage (RFC §3.2) keeps filtered-out requirements from causing false failures.

Tracing and coverage

#

The trace model itself and the coverage expectations derived from it.

SYS-TRC-001 Upstream-only trace model

#

The trace model shall be upstream-only: each requirement declares its parent(s) via the trace attribute. Downstream links are derived automatically when the graph is built across all documents. The tool shall also support trace pinning via a version integer attribute and an optional ~N suffix on trace values (e.g., SYS-042~3 means "fulfills SYS-042 version 3"). Additionally, sub-requirements receive an automatic parent-child edge from the heading hierarchy during graph construction — no manual trace attribute is needed for the parent link. V-model boundaries are inferred from document topology: directories with no upstream traces suppress untraced warnings; directories not referenced as upstream (the bottom of the V) suppress both no-downstream and generic untraced warnings.

Trace values may reference either an authored requirement ID (SYS-042~3) or a generated source-proxy ID (IMP-<package>-<Symbol>-<7hex>, optionally document-id/-qualified and ~N-pinned). Both resolve through the same graph; the built-in trace pattern admits both forms.

When multiple documents share the same ID prefix (e.g., two teams both use STK-), path-qualified trace references disambiguate: stakeholder-a/STK-001 resolves to STK-001 in the stakeholder-a/ directory. Unqualified references (STK-001) work when the ID is globally unique. An unqualified reference that matches IDs in multiple documents produces an ERROR suggesting the qualified form.

Priority
Critical
Status
approved
Rationale:

Upstream-only declarations avoid redundancy — if every child names its parent, the full chain is determined without any requirement also listing its children. Version pinning lets PR reviewers detect upstream changes since the trace was last validated. Auto-edges for sub-requirements ensure decomposition hierarchy is always present without manual attribute maintenance. V-model boundaries are inferred from directory topology (upstream.sources), eliminating per-requirement boilerplate.

SYS-FMT-005 Level-typed trace coverage

#

A requires-trace-from token shall name either a document-id or an x-reqmd.level. When a token names a level, reqmd shall resolve it to every document directory that declares that level and check that at least one approved requirement from one of those directories traces back — covering all documents at a V-model layer without listing each document-id. A token that matches neither a document-id nor a declared level shall produce a WARNING. Coverage tokens inherited from the x-reqmd.requires-trace-from document default (SYS-FMT-003) shall resolve identically: a requirement inheriting the default is subject to the same per-token checks, status gate, and filter-awareness as one declaring the tokens in its own requires-trace-from attribute.

Priority
High
Status
approved
Rationale:

Multi-document layers (e.g. several system-requirements directories owned by different teams) otherwise force every coverage expectation to enumerate every document-id. Level-typed coverage makes the V-model layer itself a first-class coverage target and stays robust as documents are added or removed within a layer.

Exports and reporting

#

The artefacts reqmd produces for reviewers and for reporting platforms.

SYS-HTM-001 Standalone HTML export

#

The HTML exporter SHALL produce a standalone page per document directory plus a project home page (index.html), with all requirement attributes, rendered prose, trace navigation, hierarchical document structure, and theme customization. The export SHALL require no network access at any point: the stylesheet and client controller are embedded, and no CDN script is loaded — with one deliberate exception, a page that contains a mermaid diagram loads the pinned Mermaid runtime so the diagram can be rendered in the browser (see SW-EXP-004). SYS-EXP-001 NDJSON tables for reporting platforms

#

reqmd export json <root> [-o <dir>] [--results <path>...] [--filter "<expr>"] shall write flat NDJSON tables for direct ingestion by reporting platforms (Databricks, Snowflake, BigQuery):

  • requirements.ndjson — one row per requirement (sections are structure, not facts, and are excluded), with built-in attributes promoted to top-level columns (version as a string, so a warehouse infers one column type) and the remaining attributes kept in an attrs envelope. Every fixed column shall be present in every row so warehouse schema inference sees the full column set: string columns are empty and collections, pin and version are null when unset. Sections still reach the fact table as context: each row carries section_path (the joined titles of its ancestor sections, empty at top level) so a reporting platform can group requirements by subsystem or chapter without a dimension table, and ordinal (1-based position within the document, unaffected by --filter) as the only authoring-order signal. Rows are ordered by document path and requirement ID; section_path groups, ordinal orders, and the row order itself is physical layout only.
  • traces.ndjson — one row per declared trace reference of an exported requirement, carrying the declared reference, the target requirement ID (never carrying a document/ qualifier, which has its own doc_id column), the pin, and whether the reference resolved.
  • results.ndjson — one row per measure verdict with its evidence cases; always written, empty when --results is not supplied.
  • findings.ndjson — one row per graph check finding.

The export shall be a pure function of the parsed tree plus results, so repeated exports of an unchanged tree are byte-identical. --filter shall scope requirements.ndjson to matching requirements while traces.ndjson and findings.ndjson stay computed over the full graph, so links into filtered-out requirements still resolve. The default output directory shall be the exported tree root.

SYS-IMP-001 Source-code requirement extraction

#

The toolchain shall include reqmd-code, a companion extraction tool that walks a source tree, dispatches each file to the tree-sitter language plugin claiming its extension, extracts top-level symbols (functions, methods, types, constants, variables) from C, C++, Go, Python, and Rust source, and extracts explicit reqmd:trace markers (and, opt-in via --heuristic-traces, bare requirement IDs from prose) from the adjacent doc comment. It shall emit a reqmd-import/v1 exchange bundle (JSON) on stdout: one document per package plus a requirement-less root document carrying the umbrella schema, with each source file a kind: section item titled by its path relative to the scanned root, each symbol a nested kind: requirement item carrying its own stable key of the form <symbol>-<hash> (hash over package+symbol so keys survive line shifts), the doc comment's prose and headings rendered as child kind: section items instead of a body, and methods nested under their type via children.

Each reqmd:trace target shall be classified as a requirement ID (emitted verbatim as a bundle ref and validated by reqmd check), a symbol reference (Name, Type.Name, pkg/Name, pkg/Type.Name, with :: accepted as .), or the reserved none opt-out. Symbol references shall resolve exactly — case-sensitively, without prefix matching — against the symbols extracted in the same run, searching the same package, then the base package of a test package (_test/test_), then a globally unique match; a qualified pkg/… search shall not fall back. An unresolved, ambiguous, or malformed directive (a target containing whitespace) shall fail the extraction with a batched diagnostic before any bundle is written.

With the opt-in --link-tests flag, a test function or method identified by the language test-file convention or an AST test marker shall additionally link to a production function, method, or type whose name is the longest boundary-valid match of the test name (Go TestX CamelCase, with initial-case folding for unexported symbols; otherwise test_x; methods spelled Type_Method, with the bare method name as a fallback that a same-named function, method, or type outranks), searched in the same package then its base package only. Explicit directives (including none) suppress convention linking for that item; an ambiguous convention match warns without failing the run.

Generated requirements shall be first-class spec documents once rendered: status: approved, x-reqmd.imported: true, provenance attributes (x-reqmd.source-file, x-reqmd.source-line, x-reqmd.symbol-kind), and IDs of the form <id-prefix><package>-<symbol>-<hash>. The generated files shall validate, export, and diff like any other spec document, closing the V-model gap from spec to code.

SYS-IMP-002 External requirement import via an exchange format

#

The toolchain shall include reqmd-import, a renderer that turns an exchange-format JSON bundle into reqmd documents (schema.yaml plus .md). The exchange format shall be a versioned, documented contract that any producer can emit — the source-code extractor, a Python script, or a direct exporter from a database-backed ALM tool (DOORS, codeBeamer) — and reqmd-import shall be the only component that writes Markdown or YAML, so quoting, heading, and schema rules exist in exactly one place.

The format shall be neutral: nothing reqmd-specific shall be required of a producer. A bundle declares its version as a $schema URL, each document carries a stable key and title, and content is a nested tree of items whose kind is either requirement (content, rendered with a reqmd block) or section (structure only, never validated, traced or counted). Nesting shall be structural rather than referential, so a cycle, an out-of-order child, or a dangling parent is unrepresentable. Requirements carry the producer's own stable key, which is unique per document and becomes <x-reqmd.id-prefix><key>; links name other items by key within the document or as <document-key>/<key> across documents and are rewritten to full requirement IDs; refs carry external requirement IDs verbatim and are never resolved. Every reqmd-specific decision (ID prefix, level, document-id, upstream, coverage expectation, external, output file) shall live in the document's optional x-reqmd block, which a producer that is not reqmd-aware omits. Attr-block properties and required fields shall be declarable per document so the generated schema.yaml accepts exactly the attributes the producer emits, and imported documents shall be renderable as external: true mirrors of content authored elsewhere.
